# 商场清洁机器人运营管理系统 · 架构基线

> WorkItem：wi-t1000005 ｜ 阶段：design ｜ 路线：simple-frontend（compact）
> 需求基线：`docs/wi-t1000005/requirements.md`（sha256:1afd01bb536d8d704bdcfd49d203861e25c5cd58365290532320cbbc4f3fc7ec）。本文档只给出承载已批准需求所需的最小技术形态，不扩展或重裁产品语义。

## 1. 应用形态

单运营人员使用的前端应用，采用 **React/Vite SPA**。无服务端：不引入服务/API、权威数据库、认证权限、后台任务、外部系统集成或跨用户/跨设备同步层。全部业务数据保存在浏览器 `localStorage` 中，在同一浏览器配置文件中刷新或重新打开页面后仍保留；不承诺跨浏览器、跨设备或跨用户可用。

## 2. 数据归属与读写边界

应用通过单一读写边界（一个状态仓库模块）管理 `localStorage`，页面不直接拼接存储键。数据模型仅覆盖已批准需求的核心实体：

- **清洁计划（plans）**：楼层、区域、作业时间、清洁模式，以及分配关联的机器人、执行状态。对应需求 §5.1、§5.2。
- **机器人清单（robots）**：内置种子数据，作为"存在可供分配的机器人"的演示前提（需求 §5.5）。仅提供可选择清单，不含档案管理功能。
- **作业报告（reports）**：任务完成后落档，内容为该次执行的可观察结果汇总：已清洁面积、任务进度、异常记录（需求 §5.4）。
- **执行期实时数据**：看板展示的当前位置、任务进度、已清洁面积、异常状态由前端模拟执行产生，仅在执行期间存在于应用状态中；其结果汇入作业报告落档（需求 §5.3）。

创建计划与分配机器人成功后写回存储并可重新读回，字段与输入一致（AC-01/AC-02 的读回基线）。

## 3. 页面与交互范围

入口统一为用户界面（需求 §6），按演示流程的四步划分功能页面，不规定具体布局：

1. **清洁计划配置**：创建计划，指定楼层、区域、作业时间、清洁模式；创建后可重新打开查看，字段一致。
2. **机器人分配**：在已创建的计划上执行分配，从机器人清单选择并确认；计划可读回与机器人的关联。
3. **实时看板**：分配后任务进入执行状态，看板展示当前位置（楼层/区域）、任务进度、已清洁面积、异常状态，并随执行推进实时更新。
4. **作业报告**：执行完成后生成报告，可查看已清洁面积、任务进度、异常记录。

## 4. 实时执行的模拟边界

需求未规定真实机器人接入方式（§5.3、§5.5），本设计以**前端模拟执行器**闭环"查看实时进度"：分配后由应用内的模拟器按时间推进产生位置、进度、面积与异常数据并驱动看板更新。该边界是设计约束而非产品语义变更；若后续要求接入真实机器人数据源，需重新评估路线。作业时间仅作为计划配置项保存，不实现按时间自动调度（需求明确未规定，不作为验收前提）。

## 5. 实现入口与运行方式

新建 React/Vite 应用，实现入口为该 SPA 的源码目录；运行方式为 Vite 开发服务器（npm 生态下 `npm run dev`）。构建产物为静态前端，不依赖任何后端进程。

## 6. 明确不包含

服务/API、权威数据库、认证权限、后台任务、外部集成、同步层、机器人档案管理、报告导出、按作业时间自动调度、清洁模式与异常类型的固定清单——均超出已批准需求范围，本次不实现。
